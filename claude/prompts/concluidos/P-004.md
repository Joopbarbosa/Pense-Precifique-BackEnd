# P-004 — DTOs: Login/Cadastro/AlterarSenha Request, AuthResponse

**Épico:** Épico 1 — Autenticação
**Camada:** back
**Depende de:** P-003 (Entity Usuario criada)

---

## Contexto para o Claude Code

Esta tarefa cria os DTOs de entrada (`request/`) e saída (`response/`) usados pelo fluxo
de autenticação. Os documentos PRD/BUSINESS_RULES v6 não detalham o Épico 1 (marcado como
"sem alterações" desde versões anteriores — o conteúdo específico de RN-001 a RN-031 não
está disponível neste contexto), então este prompt segue as **convenções gerais do projeto**
(CLAUDE.md) e o padrão usual de autenticação JWT stateless para SaaS single-tenant:

- Cada usuário (artesã) tem um único login (`email` + `senha`), conforme a tabela `usuarios`
  (campos `email`, `senha_hash`, `ativo`).
- **Não existe** cadastro de "empresa" separado nesta etapa — o cadastro de `Empresa` (perfil
  da artesã: nome do negócio, WhatsApp, endereço, logo) é tratado no Épico 2 (Configuração
  do Perfil / Onboarding), não no cadastro de usuário.
- `AuthResponse` deve retornar o token JWT + dados básicos do usuário autenticado, **nunca**
  o `senhaHash`.

**Convenções obrigatórias do projeto (CLAUDE.md):**
- DTOs separados em `request/` e `response/` — nunca expor entidade diretamente
- snake_case no banco, camelCase em Java/JSON

**Regras de negócio aplicáveis:** nenhuma RN numerada específica do BUSINESS_RULES.md
(Épico 1 marcado "sem alterações" nas versões anteriores). As validações abaixo seguem
as constraints já existentes no schema (`usuarios.email` `UNIQUE NOT NULL`, `senha_hash
NOT NULL`) e práticas padrão de segurança (senha mínima, confirmação de senha).

**Cenário de aceite:** não há cenário BDD específico para os DTOs isoladamente — eles serão
exercitados pelos cenários de login/cadastro quando o `AuthService` e `AuthController`
forem implementados (P-006/P-007). O critério de sucesso aqui é estrutural: os DTOs
compilam, têm as anotações de validação corretas (`@NotBlank`, `@Email`, `@Size`), e
`AuthResponse` não expõe nenhum dado sensível.

## Prompt

Cole este prompt no Claude Code:

---

Crie os DTOs de request e response para o fluxo de autenticação, em
`src/main/java/com/penseprecifique/api/dto/request/` e
`src/main/java/com/penseprecifique/api/dto/response/`.

Use Bean Validation (`jakarta.validation.constraints`) e, se Lombok já estiver no `pom.xml`,
use `@Getter`/`@Setter`/`@Builder` para reduzir boilerplate. Se o projeto usar `record` do
Java 21 para DTOs imutáveis, prefira `record` — escolha o padrão que for mais consistente
com o que já existir no projeto (se nada existir ainda, use `record` com validações via
anotações nos componentes do record, que é o padrão moderno recomendado para Spring Boot 3
+ Java 21).

### 1. `dto/request/LoginRequestDTO.java`
Campos:
- `email`: `String`, `@NotBlank`, `@Email` — "E-mail é obrigatório" / "E-mail inválido"
- `senha`: `String`, `@NotBlank` — "Senha é obrigatória"

### 2. `dto/request/CadastroRequestDTO.java`
Campos:
- `email`: `String`, `@NotBlank`, `@Email`
- `senha`: `String`, `@NotBlank`, `@Size(min = 8, message = "A senha deve ter no mínimo 8 caracteres")`
- `confirmarSenha`: `String`, `@NotBlank`

Não implemente a validação cruzada "senha == confirmarSenha" via Bean Validation neste DTO
(deixe para o `AuthService`, em prompt futuro, retornar erro de negócio se não coincidirem —
regra de negócio não pertence ao DTO).

### 3. `dto/request/AlterarSenhaRequestDTO.java`
Usado em `PUT /usuarios/me/senha` (endpoint futuro). Campos:
- `senhaAtual`: `String`, `@NotBlank`
- `novaSenha`: `String`, `@NotBlank`, `@Size(min = 8, message = "A nova senha deve ter no mínimo 8 caracteres")`
- `confirmarNovaSenha`: `String`, `@NotBlank`

### 4. `dto/response/AuthResponseDTO.java`
Retornado por `/auth/login` e `/auth/register`. Campos:
- `token`: `String` — o JWT gerado
- `tipo`: `String`, valor fixo `"Bearer"` (útil para o front montar o header `Authorization`)
- `usuarioId`: `UUID`
- `email`: `String`
- `expiresIn`: `Long` — tempo de expiração do token em milissegundos (vem de
  `jwt.expiration-ms` no `application.yml`)

**Importante:** `AuthResponseDTO` NUNCA deve conter `senhaHash` ou qualquer outro dado
sensível da entidade `Usuario`.

### Convenções do projeto a seguir:
- Pacotes: `dto.request` e `dto.response` (ver `CLAUDE.md`, "Estrutura de pacotes")
- Mensagens de validação em português, claras para exibição no front
- Os DTOs não devem ter nenhuma referência direta à entidade `Usuario` (desacoplamento via
  Mapper, que será criado em prompts futuros quando necessário)

### Comportamento esperado em caso de erro:
- Esta tarefa não implementa o `GlobalExceptionHandler` — apenas garante que os DTOs tenham
  as anotações de validação corretas para que o Spring retorne `400 Bad Request` com os
  detalhes de validação quando o `@Valid` for usado nos controllers (prompt futuro).

Após criar os arquivos, rode `./mvnw clean compile` para confirmar que tudo compila.
