# P-010 — Entity + Repository: Empresa, ConfiguracaoPrecificacao

**Épico:** Épico 2 — Configuração do Perfil
**Camada:** back
**Depende de:** P-003 (Usuario), P-002 (migration V1 aplicada)

## Contexto para o Claude Code

As tabelas `empresas` e `configuracoes_precificacao` já existem no banco (migration V1):

```sql
CREATE TABLE empresas (
  id                UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
  usuario_id        UUID NOT NULL,
  nome              VARCHAR(255) NOT NULL,
  email             VARCHAR(255),
  whatsapp          VARCHAR(20),
  endereco          TEXT,
  logo_url          TEXT,
  created_at        TIMESTAMP NOT NULL DEFAULT NOW(),
  updated_at        TIMESTAMP NOT NULL DEFAULT NOW(),
  deleted_at        TIMESTAMP,
  CONSTRAINT fk_empresa_usuario FOREIGN KEY (usuario_id) REFERENCES usuarios(id)
);

CREATE TABLE configuracoes_precificacao (
  id                UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
  usuario_id        UUID NOT NULL,
  valor_hora        DECIMAL(10,2) NOT NULL DEFAULT 0,
  margem_padrao     DECIMAL(5,2) NOT NULL DEFAULT 0,
  created_at        TIMESTAMP NOT NULL DEFAULT NOW(),
  updated_at        TIMESTAMP NOT NULL DEFAULT NOW(),
  CONSTRAINT fk_config_usuario FOREIGN KEY (usuario_id) REFERENCES usuarios(id)
);
```

**Contexto de negócio (PRD v6, "Metodologia de precificação"):**
> Preço = Custo dos componentes (ficha técnica) + Mão de obra (tempo × valor/hora) +
> Margem de lucro (%)

`ConfiguracaoPrecificacao.valorHora` e `margemPadrao` são exatamente os parâmetros dessa
fórmula — usados pelo `FichaTecnicaService` (Épico 4, futuro) para calcular o preço
sugerido de cada produto.

**Relação 1:1 com Usuario:** cada usuário tem exatamente uma `Empresa` (perfil) e uma
`ConfiguracaoPrecificacao` — ambas criadas no fluxo de onboarding (Tela 3), após o
cadastro (Épico 1). Não há cenário de múltiplas empresas por usuário neste MVP
(single-tenant simples).

**Convenções obrigatórias do projeto:**
- UUID como chave primária, soft delete via `deleted_at` (apenas `empresas` tem esse
  campo — `configuracoes_precificacao` não tem `deleted_at` no schema, pois faz parte
  inseparável do usuário e não é "excluída" isoladamente)
- snake_case no banco, camelCase em Java

**Cenário de aceite:** sem cenário BDD numerado específico (Épico 2 "sem alterações"). O
critério de sucesso é estrutural: as duas entidades mapeiam corretamente as tabelas, e o
Hibernate valida o schema sem erros.

## Prompt

Cole este prompt no Claude Code:

---

Crie as entidades JPA `Empresa` e `ConfiguracaoPrecificacao`, com seus respectivos
repositories, mapeando as tabelas `empresas` e `configuracoes_precificacao` já criadas
pela migration V1.

### 1. `src/main/java/com/penseprecifique/api/domain/entity/Empresa.java`

- `@Entity`, `@Table(name = "empresas")`
- Campos:
  - `id`: `UUID`, `@Id @GeneratedValue(strategy = GenerationType.UUID)`
  - `usuarioId`: `UUID`, `@Column(name = "usuario_id", nullable = false)` — mapeie como
    campo simples (UUID), **não** como relacionamento `@ManyToOne`/`@OneToOne` com
    `Usuario` por enquanto (mantém o desacoplamento simples; se necessário, um
    relacionamento JPA pode ser adicionado depois — mas para os services de Empresa, uma
    FK simples é suficiente e evita complexidade de lazy loading neste momento)
  - `nome`: `String`, `@Column(nullable = false)`
  - `email`: `String`, `@Column` (nullable)
  - `whatsapp`: `String`, `@Column` (nullable)
  - `endereco`: `String`, `@Column(columnDefinition = "TEXT")` (nullable)
  - `logoUrl`: `String`, `@Column(name = "logo_url", columnDefinition = "TEXT")` (nullable)
  - `createdAt`, `updatedAt`: `LocalDateTime`, com `@PrePersist`/`@PreUpdate`
  - `deletedAt`: `LocalDateTime`, nullable (soft delete)

### 2. `src/main/java/com/penseprecifique/api/domain/entity/ConfiguracaoPrecificacao.java`

- `@Entity`, `@Table(name = "configuracoes_precificacao")`
- Campos:
  - `id`: `UUID`, `@Id @GeneratedValue(strategy = GenerationType.UUID)`
  - `usuarioId`: `UUID`, `@Column(name = "usuario_id", nullable = false)` — mesma
    decisão de FK simples (sem `@OneToOne`)
  - `valorHora`: `BigDecimal`, `@Column(name = "valor_hora", nullable = false,
    precision = 10, scale = 2)`, default `0` (via `@Builder.Default` se usar Lombok
    Builder, ou inicialização no campo)
  - `margemPadrao`: `BigDecimal`, `@Column(name = "margem_padrao", nullable = false,
    precision = 5, scale = 2)`, default `0`
  - `createdAt`, `updatedAt`: `LocalDateTime`, com `@PrePersist`/`@PreUpdate`
  - **Sem** `deletedAt` (não existe essa coluna na tabela)

### 3. `src/main/java/com/penseprecifique/api/repository/EmpresaRepository.java`

```java
public interface EmpresaRepository extends JpaRepository<Empresa, UUID> {
    Optional<Empresa> findByUsuarioIdAndDeletedAtIsNull(UUID usuarioId);
}
```

### 4. `src/main/java/com/penseprecifique/api/repository/ConfiguracaoPrecificacaoRepository.java`

```java
public interface ConfiguracaoPrecificacaoRepository extends JpaRepository<ConfiguracaoPrecificacao, UUID> {
    Optional<ConfiguracaoPrecificacao> findByUsuarioId(UUID usuarioId);
}
```

### Convenções do projeto a seguir:
- Pacotes `domain/entity/` e `repository/`
- BigDecimal para valores monetários e percentuais (nunca `double`/`float`)
- Use `BigDecimal.ZERO` como valor padrão para `valorHora`/`margemPadrao` quando uma
  nova `ConfiguracaoPrecificacao` for criada (lógica de criação será no Service, prompt
  futuro — aqui é só a entidade)

Após criar os arquivos, rode `./mvnw clean compile` e `docker compose up --build` (ou
apenas `docker compose up` se as imagens já estiverem atualizadas) para confirmar que o
Hibernate valida o schema das duas tabelas sem erros.
