**Depende de:** P-001 (scaffold), P-002 (migration V1 aplicada)

## Contexto para o Claude Code

A tabela `usuarios` já existe no banco (criada pela migration V1, P-002):

```sql
CREATE TABLE usuarios (
  id                UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
  email             VARCHAR(255) NOT NULL UNIQUE,
  senha_hash        VARCHAR(255) NOT NULL,
  ativo             BOOLEAN NOT NULL DEFAULT TRUE,
  created_at        TIMESTAMP NOT NULL DEFAULT NOW(),
  updated_at        TIMESTAMP NOT NULL DEFAULT NOW(),
  deleted_at        TIMESTAMP
);
```

Esta tarefa cria a entidade JPA `Usuario` e seu repository. É a entidade raiz de
autenticação — todas as outras entidades do sistema (`empresas`, `clientes`, `insumos`,
`produtos`, `producoes`, `orcamentos`, etc.) têm uma FK `usuario_id` referenciando esta
tabela, pois o sistema é **single-tenant por usuário**: cada artesã (usuária) só vê seus
próprios dados.

**Regras de negócio aplicáveis:**
- **Convenção geral (CLAUDE.md):** chave primária UUID (`uuid_generate_v4()`), soft delete
  via `deleted_at` (nunca `repository.delete()`), tabelas/colunas em `snake_case`.
- **Perfis de usuário (PRD v6):** "Artesã (admin da conta): única usuária da conta — cada
  empresa tem login próprio e vê apenas seus dados." Ou seja, `email` é único globalmente
  (já garantido pela constraint `UNIQUE` no banco).
- O campo `ativo` permite desativar um usuário sem excluir o registro (diferente de
  `deleted_at`, que é soft delete). `ativo = false` pode ser usado para bloquear login
  sem apagar a conta.

**Cenário de aceite:** não há um cenário BDD específico só para a entidade (ela é a base
para os cenários de login/cadastro que serão implementados em P-006/P-007). O critério de
sucesso aqui é estrutural: a entidade mapeia corretamente a tabela `usuarios`, o Hibernate
valida o schema sem erros (`ddl-auto: validate`) ao iniciar a aplicação, e o repository
oferece os métodos de consulta necessários para o fluxo de autenticação (buscar por email).

## Prompt

Cole este prompt no Claude Code:

---

Crie a entidade JPA `Usuario` e seu repository, mapeando a tabela `usuarios` que já existe
no banco (criada pela migration `V1__initial_schema.sql`).

### 1. Crie `src/main/java/com/penseprecifique/api/domain/entity/Usuario.java`:

- Anotações: `@Entity`, `@Table(name = "usuarios")`
- Use Lombok (`@Getter`, `@Setter`, `@NoArgsConstructor`, `@AllArgsConstructor`, `@Builder`)
  se a dependência já estiver no `pom.xml`; caso contrário, gere getters/setters manualmente.
- Campos (mapeando exatamente as colunas da tabela `usuarios`):
  - `id`: `UUID`, `@Id`, `@GeneratedValue` com estratégia compatível com `uuid_generate_v4()`
    do Postgres (use `@GeneratedValue(strategy = GenerationType.UUID)` do Hibernate 6, ou
    `@Id @GeneratedValue(generator = "UUID") @GenericGenerator(...)` se necessário — escolha
    a abordagem padrão do projeto para Hibernate 6 + Spring Boot 3)
  - `email`: `String`, `@Column(nullable = false, unique = true)`
  - `senhaHash`: `String`, `@Column(name = "senha_hash", nullable = false)` — **nunca**
    expor este campo em nenhum DTO de resposta (será reforçado nos prompts de DTO)
  - `ativo`: `Boolean`, `@Column(nullable = false)`, default `true`
  - `createdAt`: `LocalDateTime`, `@Column(name = "created_at", nullable = false, updatable = false)`
  - `updatedAt`: `LocalDateTime`, `@Column(name = "updated_at", nullable = false)`
  - `deletedAt`: `LocalDateTime`, `@Column(name = "deleted_at")` — nullable, usado para soft delete

- Use `@PrePersist` para preencher `createdAt` e `updatedAt` com `LocalDateTime.now()` se
  estiverem nulos, e `@PreUpdate` para atualizar `updatedAt`.

- **Não implemente `UserDetails` do Spring Security nesta entidade ainda** — isso será
  feito em `UserDetailsServiceImpl` (prompt futuro, P-005), que vai envolver/adaptar esta
  entidade. Mantenha `Usuario` como uma entidade JPA pura de domínio.

### 2. Crie `src/main/java/com/penseprecifique/api/repository/UsuarioRepository.java`:

- Interface estendendo `JpaRepository<Usuario, UUID>`
- Métodos necessários para o fluxo de autenticação e soft delete:
  - `Optional<Usuario> findByEmail(String email)` — usado no login
  - `Optional<Usuario> findByEmailAndDeletedAtIsNull(String email)` — usado no login,
    ignorando usuários soft-deletados
  - `boolean existsByEmail(String email)` — usado na validação de cadastro (e-mail já em uso)
  - `Optional<Usuario> findByIdAndDeletedAtIsNull(UUID id)` — busca padrão respeitando soft delete

### Convenções do projeto a seguir:
- Pacote `domain.entity` para a entidade, `repository` para o repository (ver `CLAUDE.md`
  na raiz do projeto, seção "Estrutura de pacotes")
- Snake_case no banco, camelCase em Java — usar `@Column(name = "...")` quando os nomes
  diferem (ex: `senha_hash` → `senhaHash`)
- Soft delete: qualquer "exclusão" de usuário no futuro deve setar `deleted_at`, nunca
  chamar `repository.delete()`

### Comportamento esperado em caso de erro:
- Esta tarefa não envolve lógica de negócio com tratamento de erro (isso fica para o
  Service em P-006). A entidade e o repository devem apenas compilar e o Hibernate deve
  validar com sucesso o mapeamento contra a tabela `usuarios` existente.

Após criar os arquivos, rode `./mvnw clean compile` e, se possível, suba o
`docker-compose up` para confirmar que o Hibernate valida o schema sem erros
(`ddl-auto: validate` no `application.yml`) — ou seja, nenhuma mensagem de erro do tipo
"Schema-validation: missing column" ou similar nos logs do backend.
