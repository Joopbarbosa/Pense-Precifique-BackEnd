# P-005 — Security: JwtTokenProvider, JwtAuthenticationFilter, UserDetailsServiceImpl

**Épico:** Épico 1 — Autenticação
**Camada:** back
**Depende de:** P-003 (Entity Usuario + UsuarioRepository), P-004 (DTOs de auth)

⚠️ **Recomendação de modelo:** esta tarefa envolve infraestrutura de segurança (filtro
JWT, configuração de filter chain, geração/validação de token) com várias peças que
precisam se encaixar corretamente (SecurityConfig + filtro + provider + UserDetails).
Erros aqui costumam ser sutis (ex: filtro na ordem errada, exceções engolidas
silenciosamente, CORS mal configurado) e difíceis de debugar depois. Considere usar
Opus ou o modelo mais capaz disponível no seu plano para esta tarefa.

---

## Contexto para o Claude Code

Esta tarefa monta a infraestrutura de autenticação JWT stateless que será usada por
todos os endpoints protegidos do sistema (todos exceto `/auth/login`, `/auth/register`,
e o Swagger em `dev`).

**Configuração já existente no `application.yml`:**
```yaml
jwt:
  secret: ${JWT_SECRET}
  expiration-ms: ${JWT_EXPIRATION_MS:86400000}
```
Essas propriedades vêm das variáveis de ambiente `JWT_SECRET` e `JWT_EXPIRATION_MS`
(default 24h = 86400000ms), já configuradas no `docker-compose.yml` e `.env`.

**Estrutura de pacotes esperada (CLAUDE.md):**
```
security/
├── JwtTokenProvider.java        # gera e valida tokens
├── JwtAuthenticationFilter.java # intercepta requests
└── UserDetailsServiceImpl.java  # carrega usuário do banco
config/
└── SecurityConfig.java          # filter chain, CORS, permissões
```

**Regra de negócio aplicável:** "Artesã (admin da conta): única usuária da conta — cada
empresa tem login próprio e vê apenas seus dados" (PRD v6, Perfis de usuário). Isso
significa que o JWT precisa carregar, no mínimo, o `usuarioId` (UUID) e o `email`, para
que toda query nos services futuros seja filtrada por `usuario_id` (multi-tenancy lógico
por usuário).

**Convenções obrigatóras:**
- JWT stateless (sem sessão em servidor) — decisão técnica já registrada em CLAUDE.md
- `Usuario.ativo = false` ou `Usuario.deletedAt != null` deve impedir autenticação

**Cenário de aceite:** não há cenário BDD numerado especificamente para a infraestrutura
JWT (será exercitado pelos cenários de login do AuthController em P-006/P-007). O
critério de sucesso aqui é estrutural: um token gerado por `JwtTokenProvider` pode ser
validado pelo próprio provider, o `JwtAuthenticationFilter` popula corretamente o
`SecurityContext`, e requisições sem token (ou com token inválido/expirado) a endpoints
protegidos retornam `401 Unauthorized`.

## Prompt

Cole este prompt no Claude Code:

---

Configure a infraestrutura de autenticação JWT stateless do projeto, criando as classes
abaixo. Use a dependência `jjwt` (io.jsonwebtoken) já presente no `pom.xml`.

### 1. `security/JwtTokenProvider.java`

Classe `@Component` responsável por gerar e validar tokens JWT.

- Injete `${jwt.secret}` e `${jwt.expiration-ms}` via `@Value`.
- Método `String generateToken(Usuario usuario)`:
  - Gera um JWT assinado (HMAC-SHA256 ou superior) contendo:
    - `subject` = `usuario.getId().toString()` (UUID como String)
    - claim customizada `email` = `usuario.getEmail()`
    - `issuedAt` = agora
    - `expiration` = agora + `jwt.expiration-ms`
- Método `UUID getUsuarioIdFromToken(String token)`: extrai e converte o `subject` para UUID
- Método `String getEmailFromToken(String token)`: extrai a claim `email`
- Método `boolean validateToken(String token)`:
  - Retorna `true` se o token for válido (assinatura correta e não expirado)
  - Retorna `false` (sem lançar exceção para fora do método) se: assinatura inválida,
    token expirado, token malformado, ou qualquer `JwtException`/`IllegalArgumentException`
    — capture essas exceções internamente e logue em nível `DEBUG` ou `WARN`, mas não
    propague.

### 2. `security/UserDetailsServiceImpl.java`

Implementa `org.springframework.security.core.userdetails.UserDetailsService`.

- Método `UserDetails loadUserByUsername(String email)`:
  - Busca o usuário via `UsuarioRepository.findByEmailAndDeletedAtIsNull(email)`
  - Se não encontrado, lança `UsernameNotFoundException` com mensagem
    "Usuário não encontrado: " + email
  - Se encontrado, retorna um `org.springframework.security.core.userdetails.User`
    (ou implementação customizada) construído com:
    - `username` = `usuario.getEmail()`
    - `password` = `usuario.getSenhaHash()`
    - `enabled` = `usuario.getAtivo()` — **importante:** se `ativo = false`, o Spring
      Security já rejeita automaticamente o login com `DisabledException`
    - authorities: pode ser uma lista vazia ou um papel genérico `ROLE_USER` (o sistema
      não tem hierarquia de papéis — single-tenant, uma artesã = um usuário)

### 3. `security/JwtAuthenticationFilter.java`

Estende `org.springframework.web.filter.OncePerRequestFilter`.

- No método `doFilterInternal`:
  - Extrai o header `Authorization: Bearer <token>`
  - Se o header não existir ou não começar com `"Bearer "`, apenas chama
    `filterChain.doFilter(request, response)` e retorna (deixa passar — o
    `SecurityConfig` decidirá se a rota exige autenticação)
  - Se houver token:
    - Valide com `JwtTokenProvider.validateToken(token)`
    - Se válido: extraia o email via `getEmailFromToken`, carregue o `UserDetails` via
      `UserDetailsServiceImpl`, monte um `UsernamePasswordAuthenticationToken` e popule
      `SecurityContextHolder.getContext().setAuthentication(...)`
    - Se inválido: **não** lance exceção aqui — apenas não popule o contexto de
      autenticação. O `SecurityConfig` vai retornar `401` para rotas protegidas sem
      autenticação válida.
  - Sempre chame `filterChain.doFilter(request, response)` ao final (exceto em caso de
    erro irrecuperável, que não deve ocorrer aqui)

### 4. `config/SecurityConfig.java`

Classe `@Configuration` + `@EnableWebSecurity` com um `@Bean SecurityFilterChain`.

- Desabilite CSRF (API stateless)
- Configure `sessionManagement` como `STATELESS`
- Rotas públicas (sem autenticação):
  - `/auth/login`, `/auth/register` (POST)
  - `/swagger-ui/**`, `/api-docs/**`, `/v3/api-docs/**` (apenas relevante em `dev` —
    `springdoc.swagger-ui.enabled=false` em `prod` já desabilita a UI, mas as rotas
    devem ser permitidas no filtro de qualquer forma para não dar 401 confuso quando
    habilitado)
- Todas as demais rotas exigem autenticação (`anyRequest().authenticated()`)
- Adicione `JwtAuthenticationFilter` antes de
  `UsernamePasswordAuthenticationFilter` na cadeia
- Configure `AuthenticationManager` como `@Bean`, usando `UserDetailsServiceImpl` +
  um `PasswordEncoder` (`BCryptPasswordEncoder`, que também será usado no
  `AuthService` para hash de senha em prompts futuros)
- Exponha `PasswordEncoder` como `@Bean` separado (`BCryptPasswordEncoder`), pois será
  reutilizado no `AuthService` (P-006)
- Crie também um `@Bean CorsConfigurationSource` permissivo para `dev` (origem do
  frontend, ex: `http://localhost:3000`) — se já existir um `CorsConfig.java` separado
  (ver `ESTRUTURA.md`, pasta `config/`), pode integrar lá em vez de duplicar em
  `SecurityConfig`.

### Comportamento esperado em caso de erro:
- Token ausente em rota protegida → `401 Unauthorized` (comportamento padrão do Spring
  Security quando `anyRequest().authenticated()` falha)
- Token inválido/expirado em rota protegida → `401 Unauthorized`
- Usuário desabilitado (`ativo = false`) tentando logar → será tratado no `AuthService`
  (P-006); aqui basta que `UserDetailsServiceImpl` retorne `enabled = false` corretamente

### Convenções do projeto a seguir:
- Pacotes `security/` e `config/` (ver CLAUDE.md, "Estrutura de pacotes")
- Não implemente ainda o `AuthService`/`AuthController` (P-006/P-007) — esta tarefa é
  puramente a infraestrutura de segurança

Após criar os arquivos, rode `./mvnw clean compile`. Não é possível testar o fluxo
completo de login ainda (sem `AuthController`), mas confirme que `docker-compose up`
sobe sem erros de configuração do Spring Security (ex: bean `SecurityFilterChain`
carrega corretamente, sem exceções de inicialização no log).
