# P-006 — Service: AuthService (registro, login)

**Épico:** Épico 1 — Autenticação
**Camada:** back
**Depende de:** P-003 (Usuario + UsuarioRepository), P-004 (DTOs), P-005 (JwtTokenProvider, PasswordEncoder, SecurityConfig)

---

## Contexto para o Claude Code

Esta tarefa implementa a lógica de negócio de cadastro e login, usando a infraestrutura
JWT criada em P-005 e os DTOs criados em P-004.

**Regra de negócio aplicável:** "Artesã (admin da conta): única usuária da conta — cada
empresa tem login próprio e vê apenas seus dados" (PRD v6, Perfis de usuário). O cadastro
cria apenas o `Usuario` (autenticação) — o perfil da `Empresa` (Épico 2) é preenchido
depois, no onboarding.

**Validações de negócio que pertencem ao Service (não ao DTO/Bean Validation):**
- No cadastro: `senha` e `confirmarSenha` devem coincidir
- No cadastro: `email` não pode já estar em uso (`existsByEmail`)
- No login: usuário deve existir, não estar soft-deletado (`deletedAt IS NULL`), estar
  `ativo = true`, e a senha informada deve corresponder ao hash armazenado
  (`PasswordEncoder.matches`)

**Convenções obrigatórias do projeto:**
- Service: interface + impl (`AuthService` + `AuthServiceImpl`)
- Regras de negócio no Service, nunca no Controller
- Exceções de negócio devem usar `BusinessException` (a ser criada/usada em
  `exception/`, conforme `ESTRUTURA.md` — se ainda não existir, crie-a nesta tarefa como
  uma exceção simples que o `GlobalExceptionHandler` tratará no futuro)

**Cenário de aceite:** os documentos v6 não trazem cenários BDD numerados para login/
cadastro (Épico 1 "sem alterações" desde versões anteriores não incluídas neste
contexto). O critério de sucesso aqui é funcional, baseado em comportamento padrão
esperado de um fluxo de autenticação:
- Cadastro com email novo e senhas coincidentes → cria usuário, retorna `AuthResponseDTO`
  com token válido
- Cadastro com email já existente → erro de negócio (não 500)
- Cadastro com `senha != confirmarSenha` → erro de negócio
- Login com credenciais corretas → retorna `AuthResponseDTO` com token válido
- Login com email inexistente ou senha incorreta → erro de negócio genérico (não revelar
  qual dos dois está errado, por segurança — mensagem única "E-mail ou senha inválidos")
- Login com usuário `ativo = false` → erro de negócio ("Usuário inativo")

## Prompt

Crie a interface `AuthService` e sua implementação `AuthServiceImpl`, em
`src/main/java/com/penseprecifique/api/service/` e `service/impl/`, respectivamente.

### 1. `exception/BusinessException.java` (se ainda não existir)

Crie uma exceção simples:
```java
public class BusinessException extends RuntimeException {
    public BusinessException(String message) {
        super(message);
    }
}
```
Será capturada pelo `GlobalExceptionHandler` em prompt futuro (P-008 ou posterior) e
mapeada para `400 Bad Request`. Por enquanto, apenas crie a classe — não implemente o
handler ainda, a menos que ele já exista (não sobrescreva se já existir).

### 2. `service/AuthService.java` (interface)

```java
public interface AuthService {
    AuthResponseDTO register(CadastroRequestDTO request);
    AuthResponseDTO login(LoginRequestDTO request);
}
```

### 3. `service/impl/AuthServiceImpl.java`

Anotações: `@Service`, `@RequiredArgsConstructor` (Lombok) injetando `UsuarioRepository`,
`PasswordEncoder`, `JwtTokenProvider`.

**Método `register(CadastroRequestDTO request)`:**
1. Se `!request.getSenha().equals(request.getConfirmarSenha())`, lance
   `BusinessException("As senhas não coincidem")`
2. Se `usuarioRepository.existsByEmail(request.getEmail())`, lance
   `BusinessException("E-mail já cadastrado")`
3. Crie um novo `Usuario`:
   - `email` = `request.getEmail()`
   - `senhaHash` = `passwordEncoder.encode(request.getSenha())`
   - `ativo` = `true`
4. Salve via `usuarioRepository.save(...)`
5. Gere o token via `jwtTokenProvider.generateToken(usuario)`
6. Retorne `AuthResponseDTO` preenchido (`token`, `tipo = "Bearer"`, `usuarioId`, `email`,
   `expiresIn` — injete `${jwt.expiration-ms}` via `@Value` para preencher este campo)

**Método `login(LoginRequestDTO request)`:**
1. Busque o usuário via `usuarioRepository.findByEmailAndDeletedAtIsNull(request.getEmail())`
2. Se não encontrado → `BusinessException("E-mail ou senha inválidos")`
3. Se `!passwordEncoder.matches(request.getSenha(), usuario.getSenhaHash())` →
   `BusinessException("E-mail ou senha inválidos")` (mesma mensagem do passo 2, para não
   revelar se o e-mail existe)
4. Se `!usuario.getAtivo()` → `BusinessException("Usuário inativo. Contate o suporte.")`
5. Gere o token via `jwtTokenProvider.generateToken(usuario)`
6. Retorne `AuthResponseDTO` preenchido

### Convenções do projeto a seguir:
- Pacotes `service/` (interface) e `service/impl/` (implementação)
- Não crie o `AuthController` nesta tarefa (próximo prompt, P-007)
- Não crie o `GlobalExceptionHandler` nesta tarefa, apenas a `BusinessException` (se
  ainda não existir)

Após criar os arquivos, rode `./mvnw clean compile` para confirmar que tudo compila.
Testes unitários não são exigidos nesta tarefa (ficam para a Skill 8 / Test Plan), mas
